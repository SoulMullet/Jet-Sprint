# v0.7.1 — Navigation reliability and Bigfoot debugging

## What caused the navigation problem

The water geometry and checkpoint centres were on navigable water. The failure was the validation layout: 114 directional planes, about five metres apart, included gates immediately beside sharp hairpin apices. A normal rounded racing line could stay completely inside the channel while never crossing one of those planes. A reproducible six-metre rounded line failed at old gate 48, just before junction C. Wider rounded lines failed at other hairpins. The old navigator also inferred route progress from short straight chords and a gate's infinite plane, which could classify an ordinary intersection approach as a missed gate.

The same course now uses 21 directional gates (0 is the start/finish stripe). Gates are placed in unambiguous channel cross-sections clear of shared junction water and sharp apices. Startup checks the full 14.2 m gate width against neighbouring channels, favours low-curvature sections and retains a required commitment gate on every prescribed leg. Long sections retain additional gates. The boat's 13 m centre-clearance corridor fits inside those boundaries with drifting tolerance. Crossings use the swept position segment, not heading or waypoint proximity; backwards, out-of-width, adjacent-channel and out-of-order crossings do not advance the race. A crossing that begins exactly on the plane is handled explicitly.

Navigation projects onto the actual ordered route polyline within the current checkpoint corridor, including repeated visits to the same channel. It confirms progress past a missed gate or commitment to a wrong branch outside the relevant shared junction before giving recovery instructions. It does not advance gates, suppress validation or teleport the boat. Turn distance changes continuously, the existing early-turn/next-turn preview remains, and a small next-gate marker identifies the intended channel. Recovery targets follow the water route behind the gate rather than extending its tangent across an island.

## Navigation Debug

Start the game, open **Game Settings → Debug Tools**, then enable **Navigation Debug**.

- Cyan line: the complete prescribed route through the actual channels.
- Numbered boundaries and arrows: gate width and required crossing direction; gate 0 is the finish stripe. Multiple visits to the same physical gate share a combined number label.
- Lime boundary/label: the active gate. The target marker and connecting line show the boat's current navigation target.
- Status readout: approach/crossing state, target coordinates, signed distance to the plane, lateral offset, recovery reason and the last accepted/rejected crossing.

Try crossing normally, drifting through a boundary, going backwards and taking an alternative branch. Only the active gate can register. Toggle Navigation Debug off to remove its lines, labels and readout; ordinary navigation keeps only the HUD arrow and subtle target marker.

## Bigfoot encounter and debug controls

The existing dark-furred procedural Bigfoot is reused, including scale, double-throttle provocation, land-only chase, delayed airborne-spray flinch, vocal reactions and retreat. His normal encounter is now **Hidden → Walking to Shore → Watching Boat → Returning → Hidden**. Arms and legs swing with distance walked; the head/body turn toward the boat while watching for six seconds. Checked corridors lead from existing forest trees to a point roughly 3.6 m inland from the water edge. Returns retrace a checked path; chasing records a bounded land trail. The old extra oversized concealment-tree props are no longer created; existing terrain and forest generation are untouched. Site selection favours clear foreground views instead of hiding the actor behind tree crowns.

Enable **Bigfoot Debug** in the same Debug Tools section. An orange head marker, state/position/distance readout and intended path appear. **Trigger Bigfoot Now** bypasses random probability/cooldown and begins the encounter immediately, including during countdown. **Reset Bigfoot** returns him to his hidden starting position. Forced testing can find a checked land fallback if no forest corridor is suitable. Debug controls work independently of the natural encounter probability; disabling debug hides the overlays, not the encounter itself.

Both toggles default off and join the existing persistent registry/export/presets. The settings format remains schema 2: new IDs receive defaults and older values remain intact. Leaderboard storage and grouping are unchanged. No voice navigation is implemented.

## Verification and preservation

- All 16 discovered test files pass, including a new test driver that completes five laps with binary throttle/steering inputs through the unchanged boat integrator. The initial diagnostic run finished after 443.1 simulated seconds. This is automated gameplay, not a claim of human or physical-device playtesting.
- Regressions cover rounded hairpins of 6/10/14/18 m, both bank-side offsets, all gate widths, several drift crossing angles, reverse/out-of-width/out-of-order crossings, wrong-branch recovery, shared-intersection approaches and full five-lap completion.
- Bigfoot tests cover forced encounters with random sightings disabled, the entire animation cycle, limb movement, land clearance, reset, fallback, chase cooldown and delayed spray reactions.
- Chromium with mobile viewport/touch emulation verifies the toggles, touch trigger/reset, the complete Bigfoot cycle, checkpoint rejection readout, overlay disabling, reload persistence and unchanged leaderboard bytes. The formerly failing C turn shows SHARP RIGHT with its target in the intended channel and no false warning. No page/shader errors were observed. Test hooks are injected externally and do not ship.
- `npm run build` passes; the existing advisory about a JavaScript chunk above 500 kB remains.
- Exact source comparisons preserve boat physics/tuning, locked-camera presentation, water solver/surface, channel geometry, wake/spray, engine audio, controls and countdown. Gate/debug geometry is separate from the water simulation. The course layout and route sequence are unchanged; no next fluid phase is included.

Physical iPhone Safari testing is still needed for sustained performance, readability, touch ergonomics and audio/background recovery. Debug mode intentionally adds draw calls and labels; disable it for normal play and performance comparisons. Bigfoot animation is procedural, and canopy occlusion is estimated when choosing a site rather than solved by full scene visibility testing.
